# Agroecology Evidence Hub, website

**Live site: https://mlolita26.github.io/agroecology-evidence-hub/**

The website shows what happens when farmers use agroecological practices instead
of less agroecological ones. Every dot on the map is one field comparison from a
published study: a place, a crop, an agroecological practice, the alternative it
was compared with, and the effect size, lnRR. You can filter by UN region,
country, crop, outcome and practice, read the summary that is written from
whatever you picked, see the median effect by practice and outcome, and download
your selection as a spreadsheet.

Under the hood it is a static site. A Python script turns the harmonised
effect-size tables into one data file, and the browser does the rest. There is
no server and no database.

## Layout

```
build.py     reads the source CSVs and writes docs/data.js and docs/data.csv
docs/        the website itself, and the folder GitHub Pages serves
  index.html   all six pages
  styles.css   design tokens, both themes, masthead, document pages
  explore.css  toolbar, map and findings panel, heatmap, table
  app.js       routing, filtering, map, colour key, heatmap, table, CSV download
  data.js      generated by build.py, committed, do not edit by hand
  data.csv     generated by build.py, the same table as a raw file
  iso3.js      generated by build.py, country codes for the boundary files
  i18n.js      interface text in Spanish and French; English lives in index.html
  vocab.js     the data vocabulary in Spanish and French, display only
  img/         hero photographs; see img/README.md
  vendor/      other people's code, fonts and map data; see vendor/README.md
outcome_signs.csv  which way is good for each outcome, copied from the ontology
tools/
  fetch_boundaries.py     downloads and trims the country region files
  fetch_outcome_signs.py  copies the Sign column out of the ontology workbook
```

The site loads nothing from anyone else's server. Leaflet, the fonts and the
map geometry are all in `docs/vendor/`, which is the difference between a site
that still works in ten years and one that quietly stops when a CDN moves.
`docs/vendor/README.md` says where each file came from and how to update it.

Each page except the map opens with a photograph. Only the Home photograph has
a known credit so far; `docs/img/README.md` says what is missing. Remove
`data-photo` from a page header and the fallback artwork comes back: the dataset
itself, one small cell per comparison, pink for a decrease and teal for an
increase, the same colours as the map.

## Languages

English, Spanish and French, switched from the button at the top right. The
choice is remembered, and a first visit follows the browser's own language.

English is the source text: it lives in `index.html`, tagged with `data-t` keys,
and in the `KH_UI.en` block of `i18n.js` for the strings the script builds. The
Spanish and French entries in `i18n.js` override it. Any key missing from a
translation falls back to English, so a half-finished translation still gives a
working page.

To fix a wording, edit that key in `i18n.js`. To add a language, add its name to
`KH_LANGS` and a block to both `KH_TEXT` and `KH_UI`; the button picks it up.

The data vocabulary is translated too, in `vocab.js`: country, region, crop,
outcome, practice, comparator and sub-indicator names. That file is display
only. Records keep their English values, so filters still match on English and
**a CSV downloaded from the Spanish or French site is identical to the English
one**. Correct a term in `vocab.js` and it changes everywhere it appears.

Scientific binomials and index names (Shannon, Simpson, Chao1) are the same in
every language and are left alone.

The Spanish and French were produced with the rest of the site and have not yet
been checked by a native speaker, and the vocabulary has not been checked by an
agronomist. Terminology is the review team's call. Read both before the site is
promoted.

The dataset is committed, so the live site works for anyone who opens it. Two
buttons by the Comparisons heading download it: the complete dataset, always,
and the current selection once a filter is set. Both are built in the browser
from the loaded records, so nothing is fetched. It is a draft and not yet
citable; treat it as something to give feedback on, not to cite.

## The contact form

The Contact page has a form. This is a static site, so there is nothing to post
to: on submit it opens the reader's mail program with the fields already filled
in. **It needs an address.** Set `CONTACT_EMAIL` near the end of `docs/app.js`:

```js
const CONTACT_EMAIL = 'someone@example.org';
```

While it is empty the form says "The contact address is not published yet"
instead of pretending to send. Fill that in, and update the Data team and
Response time lines on the page, before the site is promoted.

If you would rather the message arrived in an inbox without the reader's mail
program opening, that needs a form service such as Formspree, which means an
account and sending the data through a third party. Worth a conversation first.

## The dataset submission form

Get involved asks people to offer a dataset. Like the contact form it opens the
sender's mail program, because a static site has nowhere to post to.

**It cannot upload files.** No browser lets a page attach a file to a `mailto:`
link. The file picker on that page only reads the names of the files chosen,
puts them in the message, and tells the sender to attach them to the email that
opens. That is honest but clumsy, and some people will not do it.

If uploads matter, the page needs a real form service. The obvious candidate is
Microsoft Forms through the CGIAR Microsoft 365 account: uploads land in
OneDrive, it costs nothing extra, and the data stays inside the institution.
Tally and Formspree also work but route submissions through a third party. Any
of them replaces the form on this page; the wording and the vocabulary lists
can be carried across.

## Rebuilding the data

Run this whenever a new synthesis is harmonised, or an existing one changes:

```
python build.py
```

It reads every CSV in the clean effect-size folder:

```
Agroecology_Evidence_Hub/02.FOMD/04.metadata_effectsize/03.fomd10_clean
```

and prints how many records each source contributed, how many comparisons it
turned round so that the agroecological arm is the practice, and how many it set
aside because neither arm was agroecological (see "What one record is" below).
`python build.py --dry-run` prints all of that and writes nothing, which is the
way to check a new source before publishing it. If your copy of the Hub is
somewhere other than the default OneDrive path, edit `SOURCE_DIR` at the top of
`build.py`. Only the standard library is needed, so there is nothing to install.

It also says how many comparisons have no known good direction, and names any
sub-indicator that has neither a `Sign` in the ontology nor an entry in
`SIGN_FIXES`. When the ontology's `01_outcomes` sheet changes, refresh the copy
the build reads with `python tools/fetch_outcome_signs.py` (this one needs
`openpyxl`; it opens the workbook read-only and never writes to it).

It also tells you when a country in the data has no boundary file, and prints
the command that fetches one:

```
python tools/fetch_boundaries.py BRA NGA
```

Then commit the regenerated files and push; GitHub Pages redeploys on its own.

### Which syntheses are published

Every CSV in that folder is published unless it is named in `SKIP_SOURCES` at
the top of `build.py`, with the reason written next to it. Leaving a synthesis
out is meant to be a decision someone recorded, not something that happened
quietly. Delete the entry to publish it.

ERA is skipped at the moment, for two unrelated reasons that are both in the
comment: it is far too large to send to a browser as one file, and its effect
sizes come from a script with an open bug. The build prints the reason every
time it runs, so nobody has to go looking for it.

### When the build stops

The whole dataset is sent to the browser as one file, so its size is the page's
load time. If what is published grows past what that can carry, `build.py`
writes nothing, says so, and leaves the last dataset that fit in place. The site
keeps working, and no one accidentally publishes a page that takes a minute to
open.

That is not a limit to raise. It means the data has outgrown a single file and
needs a real format behind it, which is a piece of work to plan, not a number
to change in `MAX_DATA_MB`.

## Viewing the site locally

```
python -m http.server -d docs 8000
```

and open <http://localhost:8000>. Opening `index.html` straight from the file
system also works, but a local server is closer to the real thing.

## What one record is

One comparison between an agroecological practice and a less agroecological
alternative, for one outcome, at one place.

- `practice` is always the agroecological arm and `comparator` the alternative.
  The sources label their arms control and treatment their own way, and
  sometimes the conventional arm is the "treatment". `build.py` turns those
  round before computing anything: if the source's treatment carries a term
  from `COMPARATOR_TERMS` (monoculture, conventional tillage, mineral
  fertiliser, synthetic pesticide, no input at all, and so on) and the control
  does not, the arms are swapped and `swapped` is true. If both arms carry one,
  neither is agroecological, and the comparison is set aside and not published.
  The build prints every swap and every pair set aside, so the list can be
  checked against the data. The list follows the draft scoring rule in
  `knowledge/control_treatment_scoring.md`; it is Andrea's to ratify.
- `pillar` and `subPillar` are the two levels of the outcome ontology above the
  indicator; `group` is the organism counted, for biodiversity outcomes.
  Together they are how the heatmap groups and names its columns.
- `lnRR` is `ln(T/C)` with T the agroecological arm, exactly as computed from
  the two means. `direction` says which way is good for that outcome: +1 where
  higher is better (yield, income, richness), -1 where lower is (costs,
  erosion, pests, weeds), 0 where nobody has said. It comes from the `Sign`
  column of the ontology's `01_outcomes` sheet, copied into `outcome_signs.csv`
  by `tools/fetch_outcome_signs.py`, plus two things written in `build.py`:
  the obvious reading of the four sub-indicators the ontology leaves blank
  (`SIGN_FIXES`), and a rule for Abundance, which the ontology marks "higher
  is better" although more weeds or pests is worse (`BAD_ORGANISMS`). Both
  belong in the workbook eventually.
- `yi` is `lnRR × direction`: the effect size the analysis uses, turned so
  that positive always means the agroecological arm did better. It is what the
  map, the heatmap and the summary sentence show. `se` is its standard error
  and `vi` its variance, the names R's `metafor` uses; both are empty where
  the source reported no usable dispersion, which is most of Paut. `yi` is
  empty where `direction` is 0, and those points are grey.
- `value` is the percentage change of T against C. It is in the download as a
  reading aid and shown nowhere on the site.
- `KH_COLUMNS` in `data.js` is the column order of `data.csv` and of the
  download button; `app.js` reads it rather than keeping its own list.
- Rows are dropped when they have no coordinates, no positive control mean, or
  no practice contrast.

Statistics on the site are medians of lnRR across comparisons, labelled as
such. They describe the selection; they are not a pooled meta-analytic estimate.

## Scope

The Hub is global. Which countries appear depends on which syntheses have been
harmonised so far, not on any geographic limit. Reporting follows ROSES.

## Publishing

The site is served by GitHub Pages from the `docs/` folder on `main`.
Push to `main` and the change is live in a minute or two.

GitHub Pages sends `Cache-Control: max-age=600`, so without help a browser can
show an old stylesheet or script for ten minutes after a change. `build.py`
handles this: it tags each asset link in `index.html` with a hash of that
file's contents, so a changed file gets a new URL and is fetched at once, and
an unchanged one keeps its URL and stays cached.

**So run `python build.py` before you commit, even when the data has not
changed.** It is what refreshes those tags. Never edit the `?v=` values by
hand: a number someone has to remember to bump is the bug this replaces.
